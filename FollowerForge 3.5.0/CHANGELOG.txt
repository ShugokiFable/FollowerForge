## [3.1.1] - 2026-08-05 - say so when a preset's shape cannot become a follower
Agent: Claude
Parent: FollowerForge 3.1.0

Runtime basis:
  - User report: a FaceForge-generated preset looked right on their own character but the
    follower built from its exported head came out flat and unlike it.

Investigation (all measured on the user's own install, nothing inferred):
  - The shipped FaceGen mesh is a byte-exact copy of the RaceMenu export: same 7 shapes, same
    vertex counts, and FaceGenRoundTripTests compares every vertex.
  - The head is High Poly Head (00KLH_FemaleHeadImperial, 3832 verts) and IS deformed from the
    HPH base mesh - 99.5% of vertices moved.
  - The facegeom/facetint are deployed under the same naming every installed follower mod uses
    (00000800.nif for an ESPFE), the plugin is enabled, and the NIF's tint slot was rewritten
    to the generated facetint.
  - The face tint DDS is 512x512 uncompressed 32-bit, byte-for-byte the same form as every
    author-made follower's.
  - NPC QNAM matches the tint's median colour, which is exactly what real follower mods do:
    sampled 24 installed NPCs and QNAM equals the tint median on all of them.
  So nothing FollowerForge writes is wrong.

Root cause, upstream:
  - The preset carries 99 RaceMenu slider values (CME_/EFM_/SPG_) and ZERO sculpt deltas. The
    working preset on the same machine carries 944.
  - Not one of those slider names exists as a vertex morph in ANY deployed chargen .tri -
    checked both the vanilla and the High Poly Head one; both hold only the vanilla morph names.
    They are node transforms applied to a live actor, which is why the jslot stores them beside
    a "transforms" block the generated preset does not have at all.
  - Only two things can reach an NPC's face: the vanilla 19 morphs, which go on the record, and
    geometry, which bakes into the exported head. Slider-only shaping is neither, so it cannot
    survive the trip however the follower is built.

Added:
  - The preset reader now counts non-zero sliders and sculpted vertices separately.
  - A build warning, FACE_SLIDERS_WITHOUT_SCULPT, fires when a preset has 10+ sliders and no
    sculpt at all, and names the fix (sculpt anything in RaceMenu before exporting the head).
  - The face picker marks such an export NO SCULPT with the same explanation, so it is visible
    at step 2 rather than after a build.
  - Verified against the real preset: the warning fires and reads "99 RaceMenu slider values
    and sculpts nothing".

Files:
  - src/AssetIndex/CharGenDiscovery.cs, src/Domain/FollowerProfile.cs
  - src/BuildPipeline/FollowerBuilder.cs, src/Ui/PickerItem.cs
  - src/Tests/SliderOnlyPresetTests.cs (new)

Verify: 278 tests pass (275 at 3.1.0 + 3).
Runtime: the warning is static analysis of the preset; the flat face itself is upstream and
  is fixed by re-exporting the head with sculpt data present.
Nexus: NO (local tool)

## [3.0.0] - 2026-07-29 - the follower suite
Agent: Claude
Parent: FollowerForge 2.1.3

Everything below this entry shipped during 2.1.3's development and is released as 3.0.0.
Headline: custom voiced dialogue, contextual reactions, vampires, werewolf and mod
transformations, creature followers, enemy-to-ally, optional evolution, random spawns,
NPC relationships, AI routines, lore inventory, and marriage reporting read from the
actual load order.

DISMISS / GOING HOME - verified rather than assumed. Vanilla's dismiss is only:
    AddToFaction(pDismissedFollower)
    SetPlayerTeammate(false)
    RemoveFromFaction(pCurrentHireling)
    EvaluatePackage()
  There is no MoveTo and no editor-location call anywhere in it, so where a dismissed follower
  goes is decided ENTIRELY by her AI package. Ours already gives her a sandbox package, so she
  settles where she was placed - which is why this appeared to "just work".

  That exposed a real bug: an EDITOR-location sandbox sends her back to her ORIGINAL placement,
  which is wrong once something has moved her. A randomly-spawned or enemy-to-ally follower would
  walk cross-country back to a marker after being dismissed. Those followers now get
  SandboxCurrentLocation256 instead, so they settle wherever they actually are.

  Note for "Leave it to the game": with no package at all, nothing directs her after dismissal.
  Follower frameworks (NFF, My Home Is Your Home) override all of this anyway once the player
  sets a home in game.

SCRIPTED-FOLLOWER WARNING. Any build carrying one of the four optional scripts now emits
  SCRIPTED_FOLLOWER once, and the experimental panel says the same: scripted followers can behave
  oddly if also imported into a follower framework. Ordinary followers are unaffected.

RELEASE STATUS - stated plainly rather than implied:
  Record-only features are evidence-backed and structurally verified against shipped mods.
  The four SCRIPT features (evolution, transformation, random spawn, enemy-to-ally) compile and
  bind correctly but have NEVER been confirmed running in Skyrim. test-in-game.txt ships with
  every follower and names the exact symptom of failure for each.

## [3.0.0 development] — 2026-07-25 — face pairing fix + voice-synthesis groundwork
Agent: Claude

FACE MATCHING BUG (user-reported): 'A1_Imperial_Matilda_head' failed at BUILD time with
  "has a head export but no readable matching jslot ... re-save the preset" — but the preset
  existed all along as 'A1_Imperial_Matilda_Replacer.jslot'. Pairing only stripped a trailing
  "_head", so any preset saved with a different decoration was missed and the advice given to
  the user was simply wrong. NormalizeKey now peels head/replacer/sculpt/preset/chargen/export/
  final/face repeatedly, then falls back to a single UNAMBIGUOUS prefix match; equal-length
  rivals are left unmatched rather than guessed, because pairing a face with the wrong preset
  would silently build the wrong follower.
  Measured on this machine: 16/20 usable -> 20/20 usable
  (recovered: Matilda, High Elf Eva, Samantha via "_Replacer"; Morya via "Sculpt").

LOOK STEP now states readiness up front. CharGenExport.Blocker/IsUsable is the single source of
  truth shared by the picker and the builder, so a face can no longer read "tint OK" at step 2
  and then fail with FACE_PRESET_MISSING at step 7. Unusable faces sort last, read
  "CANNOT BUILD: <reason>", and selecting one warns immediately. New CLI: `fforge faces`.

VOICE SYNTHESIS GROUNDWORK (toward optional custom lines in step 3):
  AssetIndex/VoiceModelCatalog.cs maps voice types onto installed xVASynth models
  ("FemaleEvenToned" -> "sk_femaleeventoned") and locates the lip/fuz tools.
  New CLI: `fforge voices`. Measured: 105 models, 46 of 1018 voice types speakable,
  lip/fuz toolchain present.
  Verified by direct inspection (NOT assumed):
    - xVASynth serves a local HTTP API on port 8008. Standalone server is
      resources/app/cpython_cpu/server.exe and MUST run with cwd = resources/app
      (it loads ./javascript/script.js and exits otherwise). Confirmed by starting it.
    - Synthesis endpoints: /synthesize, /synthesizeSimple, /synthesize_batch.
      /synthesize takes {pluginsContext, modelType, sequence, pace, outfile, vocoder}.
      /loadModel takes {model, modelType, pluginsContext}.
      /outputAudio is the post-process hook lip_fuz attaches to, NOT the TTS call.
    - lip/fuz chain, commands read verbatim from plugins/lip_fuz/main.py:
        FaceFXWrapper.exe <game> USEnglish FonixData.cdf "<wav>" "<resampled>" "<lip>" "<text>"
        xWMAEncode.exe -b 160000 "<wav>" "<xwm>"
        fuz_extractor.exe -c "<fuz>" "<lip>" "<xwm>"
    - Shipping layout confirmed against Laci Living Doll (1,674 .fuz):
        sound/voice/<Plugin>.esp/<VoiceType>/<quest>_<topic>_<INFO FormID 8hex>_1.fuz
        plus SEQ/<Plugin>.seq
VOICE PIPELINE, first vertical slice:
  SkyrimRecords/DialogueAssets.cs — VoiceFileNaming + SeqWriter, both derived from a shipped mod
  rather than assumed. The two conventions differ in a way that fails SILENTLY:
    - .fuz filename uses the record's LOCAL id with the master index ZEROED
      (INFO 0700082B -> "…_0000082B_1.fuz"). Wrong form = follower mouths a line with no sound.
    - .seq entries keep the plugin's OWN master index (07000801), little-endian, no header,
      no signature. Wrong form = the dialogue quest never starts, with no error.
  AssetIndex/VoiceSynthesizer.cs — starts xVASynth's server (cwd must be resources/app),
  /loadModel + /synthesize, then FaceFXWrapper -> xWMAEncode -> fuz_extractor. Only stops a
  server it started itself, so a user's own xVASynth session is left alone.

  BUG CAUGHT BY TEST: SeqWriter first wrote Mutagen's FormKey.ID directly, producing 00000801
  where the game needs 07000801 — Mutagen's ID carries only the 24-bit local id, so the plugin's
  master index must be supplied. Now an explicit required parameter, and the test asserts the
  output byte-for-byte against Laci's real abcd_laci.seq.

  PIPELINE PROVEN END TO END, 13.1s for one line (CPU):
    server ready 10.1s (cold) | loadModel 200 in 2.1s | synthesize 200 in 0.5s -> 75,820-byte wav
    FaceFXWrapper 0.3s -> 1,842-byte .lip | xWMAEncode + fuz_extractor -> 17,546-byte .fuz
    magic FUZE, lipSize 1842 (non-zero = the mouth actually moves)

  MY FIRST CLIENT WAS WRONG AND HUNG. Corrected against Mantella's xvasynth.py, which drives the
  same server fast enough for live conversation:
    - address must be 127.0.0.1, NOT "localhost" — that resolves to ::1 first on Windows and the
      connection stalls rather than failing fast. This is what left a test polling for hours.
    - liveness is a plain GET "/" ; POSTing /checkReady with a guessed body throws server-side
      and proves nothing.
    - the server is launched with cwd at the xVASynth ROOT (not resources/app).
    - /synthesize must carry the model's own base_emb (games[0].base_speaker_emb from the model
      json, flattened) plus base_lang/useSR/useCleanup, or an xVAPitch model returns unusable audio.
      VoiceModel now carries BaseSpeakerEmb; sk_femaleeventoned is modelType "xVAPitch".
    - FaceFXWrapper runs from the lip_fuz folder with a RELATIVE FonixData.cdf. We deliberately do
      NOT copy Mantella's trick of writing run_mantella_command.bat into the xVASynth install —
      that is someone else's installed tool.
    - xWMAEncode warns "bitrate 160000 -> using 48000"; harmless, matches what Mantella ships.
    - THE ACTUAL KILLER, found in xVASynth's own server.log: every request was silently doing
      nothing because server.py line 155 runs int(self.headers['Content-Length']) unconditionally,
      and .NET's JsonContent streams CHUNKED with no Content-Length, so the handler threw before
      reading a byte. Python's requests always sends the header, which is why Mantella never hit
      it. Now serialised to a buffered StringContent so the length is set.
    - The server also closes the socket without framing a reply; Python shrugs, .NET raises
      HttpIOException. Treated as "delivered" and verified by the output file instead, matching
      Mantella's own "Connection aborted ... So it is alive" handling.
  C# end-to-end test now passes in 809ms against the real install (server already warm).

CUSTOM DIALOGUE, END TO END. Records, audio, and the step-3 UI are now wired together, so a
  follower built from the wizard actually speaks lines the user wrote.

  Structure copied from a shipped follower mod (Laci Living Doll: 8 quests, 43 topics) by
  dumping its records with Mutagen, not reconstructed from documentation:
    - QUST flags 0x11 (StartGameEnabled + the unnamed bit the CK always sets), priority 0,
      type None, ZERO aliases.
    - The "is this the right speaker" test lives ONCE on the quest (DialogConditions), not on
      every INFO.
    - Hello -> HELO/Misc, Goodbye -> GBYE/Misc, Idle -> IDLE/Misc; a player-pickable topic is
      CUST/Topic and needs a TopLevel DialogBranch or it never appears in the menu.
    - INFO flags Random (alternatives), plus Goodbye on a player topic.

  DELIBERATE DEPARTURE from how shipped follower mods do it: Laci gates dialogue on
  GetIsVoiceType, which is safe only because she ships a bespoke voice type nobody else has.
  FollowerForge offers STOCK voices, so that same condition would put the user's custom lines
  in the mouth of every Nord woman in Skyrim. We gate on GetIsID against the generated NPC,
  which is exact whichever voice was picked. Pinned by test.

  SEQ INDEXING FOR LIGHT PLUGINS — checked rather than assumed. An ESPFE's records live at
  runtime FormIDs FE-xxx-yyy, so the SEQ could plausibly need that form. It does not. Surveyed
  every shipped .seq in this install: 926 quest FormIDs across 215 plugins, 182 of them
  ESL-flagged, and EXACTLY ZERO use the FE form. The in-file master-count index is correct for
  light and regular plugins alike.

  Dialogue records are allocated LAST, so adding lines to an existing follower does not shift
  her NPC/ACHR FormIDs and break saves that reference her. Pinned by test.

  CHILD VOICES ARE REFUSED (SkyrimRecords/VoiceSuitability.cs). Enforced in the BUILD, not just
  hidden in the wizard, so a hand-written profile or a CLI build cannot route around it.
  "child"/"kid" match anywhere; "boy"/"girl" only as whole words so a name like "Boyle" is not
  a false positive. Measured: 12 of 1,004 installed voice types blocked. Verified by building
  with FemaleChild -> VOICE_UNSUITABLE, BUILD FAILED (not published).

  Failures here are ERRORS, not warnings, on purpose: a follower whose quest silently never
  starts, or whose lines are mute, looks identical to a working one until you are standing in
  front of her in game. Turning synthesis off deliberately is a warning instead.

  MEASURED END TO END (`fforge build`, 4 lines across 3 topics):
    Voiced 4/4 lines | SHIP_GATE_PASS HEDR=1.71 numRec=26 ESL=True
    4x .fuz written to sound/voice/FF_VoiceProbe.esp/FemaleEvenToned/, all magic FUZE with
    lipSize 1119-2509 bytes (non-zero = the mouth moves)
    SEQ = 01000803: quest local 0x803 at master index 1 (1 master), 4 bytes

SILENT DIALOGUE FIXED (user-reported: "the mouth keeps moving for too long ... there is 0 audio").
  Both symptoms were ONE bug, and not the one they look like. The engine builds a voice filename
  from the quest EditorID cut to 10 characters and the topic EditorID cut to 15. We wrote full
  names, so the file was never found — you get the subtitle and a generic mouth animation of
  default length, which reads as broken lip sync rather than a missing file.

FIXED (user-reported): GARBLED TEXT THROUGHOUT THE WIZARD, and it was self-inflicted in the
  previous fix. Editing WizardWindow.axaml with PowerShell 5.1's Get-Content/Set-Content mangled
  it: Get-Content reads a BOM-less UTF-8 file using the system ANSI code page, so every em dash,
  ellipsis and arrow decoded into three Latin-1 characters, and Set-Content wrote those back as
  UTF-8 - double-encoding them. 29 lines affected. Nothing failed to build; the app simply
  displayed the garbage.

  Repaired by reversing the transform exactly (re-encode to the ANSI code page, decode as UTF-8)
  rather than hand-patching strings, and the file is now stored WITH a BOM so the same tool
  cannot misread it again. Recovered characters verified on disk: U+2014, U+2026, U+25C0, U+25B6.

  Two things went wrong in the repair itself, both worth recording:
   - The first attempt aborted on byte 0x9D. Python's cp1252 codec rejects the five positions the
     code page leaves undefined, while .NET maps them to the matching control code points; the
     reverse table needs those five or the repair refuses real files.
   - The second attempt looked like it was CORRUPTING good text, because it printed recovered
     characters to a cp1252 console. The diff was misleading, not the transform.

  New guard: Tests/SourceEncodingTests scans every .cs/.axaml/.csproj/.psc/.md/.txt for the
  double-encoding signatures. Confirmed it fails on the actual damaged file
